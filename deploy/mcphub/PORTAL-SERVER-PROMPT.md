# Official MCPHub with Canvas Portal: server deployment task

Restore the independent Canvas Portal at https://canvas.mcp.kazuhahub.com and connect it to the official MCPHub at https://mcp.kazuhahub.com using personal upstream OAuth. Do not deploy the custom MCPHub reminder fork or modify the official Hub image/source. The Portal owns Canvas tokens and expiration reminders; the Hub only holds each user's delegated OAuth grant. Leave Anteater and other existing servers intact.

## Inspect and back up

Locate the actual Compose projects, service names, reverse proxy, old Canvas data volume/database, runtime-secrets.json or explicit keys, and prior environment-file backups. Inspect secrets locally without displaying them. Back up Hub data/credential-encryption key, Canvas data/database/keyring, Compose/env files and proxy configuration with private permissions. Do not run down -v, overwrite keys, initialize over an old database, or delete existing Hub personal bindings. If Canvas's old data/keyring was deleted, report that credentials and preferences cannot be recovered; create a fresh Portal only after explaining that users must enroll again.

## Restore Canvas Portal

Use the published fork source https://github.com/KKazuhaK/canvas-mcp, release v1.14.1, image ghcr.io/kkazuhak/canvas-mcp:1.14.1. Read deploy/selfhost/README.md and reuse the original Compose/env/proxy configuration wherever possible. If this release would downgrade a newer running/persisted schema, stop and identify the compatible image instead. Restore the original volume and keys together. For a fresh installation use deploy/selfhost/docker-compose.yml and env.example with PUBLIC_BASE_URL=https://canvas.mcp.kazuhahub.com, retaining the single-replica, loopback-bound, read-only defaults. The Compose file defaults to beta: explicitly pin the reviewed version or digest in CANVAS_MCP_IMAGE.

Forward the complete Canvas origin to the service, including /account and its assets/API routes, /mcp, /.well-known/, /authorize, /token, /register and /revoke. Preserve HTTPS, host/proxy handling and uncached OAuth responses. Verify /api/v1/version and OAuth discovery against the running service. Existing installations use the database-owned public URL and login settings; do not expect changing env to overwrite them. Restore prior login providers and mail settings from their database instead of inventing new ones. For a fresh installation let the owner complete /account/setup using the installation code privately, then configure permitted schools and account admission.

## Email and user journey

The Portal already includes SMTP settings and user notification preferences. Inspect its actual admin settings UI/API and existing configuration; do not apply MCPHUB_SMTP_* variables from the abandoned Hub fork. Reuse a previously authorized SMTP configuration only when appropriate. If missing, ask the owner to enter SMTP host/port/user/password/from through the Portal's supported admin interface; never print passwords or disable TLS verification. Enable the operator's reminder service, then let each user opt in and set their own reminder email at /account/token#reminders. Do not silently subscribe other users or send test mail to third parties. Verify real inbox delivery separately from configuration and metadata discovery. Unknown token expiry must remain visibly unknown; do not invent an expiration date or promise reminders without discoverable metadata.

Users visit https://canvas.mcp.kazuhahub.com/account/token to select their school and bind their own Canvas token once. They acknowledge the custody notice themselves. They then return to MCPHub → Servers → Canvas → Connect to sign in to the Portal and consent to their own grant. Future token replacement happens in the Portal; revocation/rotation may require reconnecting the Hub grant. Do not promise that every token rotation is transparent.

## Connect stock MCPHub, with a reversible transition

First add a separate trial server named canvas-portal using Streamable HTTP, URL https://canvas.mcp.kazuhahub.com/mcp, public visibility for authenticated Hub users, oauth.identityMode=personal, and scopes=["Canvas.Access"]. Example: deploy/mcphub/mcp_settings.portal.example.json. Set the actual owner to the existing operator account, not a guessed admin. Add no shared OAuth tokens, Canvas token headers or manual credentialTemplate. Personal OAuth is separate from the Hub's existing client-facing OAuth server; preserve both sides' state and callback routing. Use the official dashboard's Each user authorizes independently setting and Connect flow. Do not inspect/copy raw tokens from the Hub encrypted credential store into the Portal.

Verify with two separate consenting test users: each can authenticate, authorize and obtain only their own get_my_profile result; an unbound user must receive Personal authorization required rather than another user's data. Verify the expected 48 read-only student tools and no write/code-execution tools. Use user-associated Hub credentials, not a shared/system key. Do not claim the integration works based on discovery alone.

Only after that end-to-end check succeeds, preserve the old canvas-personal server definition/binding backup, disable its stdio definition to prevent duplicate tool sets, and either use canvas-portal as the published route or migrate the validated definition to canvas-personal to preserve external URLs. Changing the identity mode invalidates previous manual bindings and requires every user to Connect once; warn before the cutover. Do not delete the old bindings as part of the trial. If authorization fails, keep the old stdio entry active and report the concrete error with secrets removed. Leave Anteater unchanged.

## Upgrade and rollback

Keep MCPHub on its official image, record the exact current digest, and retain its persistent volumes and encryption key across normal upgrades. The Portal is updated independently using its own versioned image and backups. This removes a custom-Hub merge requirement; upstream compatibility changes still require ordinary smoke tests. Never auto-replace the Hub with KKazuhaK/mcphub's custom reminder branch. If a custom Hub was already installed, back up first and return to the compatible official 1.1.10 image before validating the new upstream connection.

Rollback the connection by disabling canvas-portal and re-enabling the saved canvas-personal stdio definition. Keep data/keyring and old images; do not delete volumes or downgrade a migrated Portal database without restoring its matching backup. Report the actual image digests, backup paths, Portal health, discovery, two-user authorization results, email configuration and inbox-delivery status, final public route, and any user action still needed. No tool/agent attribution in repository artifacts.
